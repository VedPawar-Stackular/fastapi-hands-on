Critical

1. Declared a dict, used it like a list

TL;DRfiltered_ticket = {} then filtered_ticket.append(...) — dicts have no .append(). Crashes with AttributeError.

What happened

filtered_ticket was created as an empty dict ({}). Later code called filtered_ticket.append(...) on it. Dicts don't have .append() — only lists do.

Piece by piece

PieceMeaning
{}empty dict literal — key → value storage
[]empty list literal — ordered sequence storage
d.append(x)invalid — dicts don't support this method at all
l.append(x)valid — adds x to end of list l
d[key] = xvalid — sets/overwrites value at key in dict d
Before (broken) 
filtered_ticket = {}   # dict
...
filtered_ticket.append(Ticket(id=ticket_id, **ticket.model_dump()))  # dict has no .append
After (fixed) 
filtered_ticket = []   # list, matches what you're actually building
...
filtered_ticket.append(Ticket(id=ticket_id, **ticket.model_dump()))

Why it happened

Own comment said "my thought process is to make a dict to store all the filtered tickets, but I am not sure if this is the best approach." That uncertainty was the signal to stop and ask: insert-by-key, or grow-a-sequence? Container was picked before the usage pattern was decided.

How to avoid it next time

  • Pick container by how you'll use it. Need lookup by key later → dict. Just collecting matches in order → list.
  • Not sure? Write the loop body first (.append(...) vs. [key] = ...) — that reveals the container it needs.
  • Run the endpoint once. This error shows up on the very first real request.
💡 Learn this: Python containers aren't interchangeable — dict, list, set, tuple each support different operations. Mixing the mental model of one with the syntax of another is one of the most common beginner bugs. Ask "what am I storing this for?" before typing the declaration.

2. Subscript access on a Pydantic model (ticket[priority])

TL;DRticket is an object, not a dict. Use ticket.priority, not ticket[priority]. The latter raises TypeError.

What happened

ticket is a Ticket instance (a Pydantic BaseModel), not a dict. Pydantic models expose fields as attributes, not subscriptable keys. ticket[priority] tries to index the object using the value of variable priority (e.g. the string "HIGH") — something Ticket has zero support for.

Piece by piece

PieceMeaning
ticketa Ticket object (Pydantic model instance)
prioritya plain string variable, e.g. holds "HIGH"
ticket[priority]tries ticket["HIGH"] — indexing not supported on Ticket → TypeError
ticket.priorityreads the actual priority field off the object → correct
Before (broken) 
if ticket[priority] == priority:      # TypeError — Ticket isn't subscriptable
After (fixed) 
if ticket.priority == priority:       # dot access reads the field

Why it happened

Likely muscle memory from dicts — tickets_db[ticket_id] is used correctly elsewhere, since tickets_db genuinely is a dict. File mixes a raw dict (tickets_db) with Pydantic objects (Ticket), easy to apply dict syntax everywhere.

How to avoid it next time

  • Before x[y] or x.y, ask: "what type is x right now?" From tickets_db.items(), the second tuple element is a Ticket → dot access.
  • Editor autocomplete confirms it — type ticket. and see field suggestions.
  • A type checker (mypy/pyright) flags ticket[priority] before you ever run it.
💡 Learn this: obj[key] requires the class to implement __getitem__ (dicts, lists, opt-in custom classes). Pydantic models don't — each field is a real attribute with a defined type. Dicts are for dynamic/arbitrary keys; model attributes are for a fixed, known schema.

3. Comparing to the wrong variable

TL;DRticket[priority] == priority compares a value to itself, conceptually. Needed ticket.priority == priority — ticket's own field vs. the filter.

What happened

Even fixing the subscript issue alone isn't enough — the intent was "does this ticket's priority field equal the priority the caller asked to filter by." That needs the ticket's own .priority field compared against the function parameter priority — two different things sharing one name.

Traced with real values

priority = "HIGH" ← query param passed by caller ticket.priority = "MEDIUM" ← this particular ticket's actual field ticket[priority] == priority → TypeError (mistake #2, crashes before comparing) ticket.priority == priority → "MEDIUM" == "HIGH" → False (correct — ticket filtered out)
Before (broken logic) 
if ticket[priority] == priority:   # comparing "ticket's field at key=priority" to "priority" itself
After (correct logic) 
if ticket.priority == priority:    # ticket's own priority field vs. the filter the caller passed in

Why it happened

Reusing the name priority for both the query parameter and the field being compared makes it easy to lose track of which is which mid-expression. Not really a syntax bug — a "didn't read the condition out loud" bug.

How to avoid it next time

  • Say the conditional in plain English first: "keep this ticket if its priority field matches the priority the user asked for." Translate that sentence field by field.
  • Watch for name collisions between function parameters and object fields — easy to accidentally write x == x-shaped code when they share a name.
  • Trace with a concrete example (see table above) before trusting the logic.
💡 Learn this: Logic bugs like this survive type checkers and linters — code runs fine, just returns wrong tickets. "Does it run" is a lower bar than "does it do what I meant." Always mentally run the condition with a real example before trusting it.

4. response_model shape didn't match what was returned

TL;DRresponse_model=Ticket promises one ticket. Function returns many. Use response_model=List[Ticket] for collection endpoints.

What happened

@app.get("/tickets/", response_model=Ticket, ...) declared the response as a single Ticket. The function actually returns tickets_db.values() or filtered_ticket — plural, not singular. FastAPI treats response_model as a strict contract for validating/serializing the return value; forcing a list into a single-object schema fails or mis-serializes.

Piece by piece

PieceMeaning
response_model=Ticket"this endpoint returns exactly one Ticket-shaped object"
response_model=List[Ticket]"this endpoint returns a list of Ticket-shaped objects"
tickets_db.values()dict view of all Ticket objects — many, not one
List[Ticket]typing generic — List from typing, parameterized with element type Ticket
Before (broken) 
@app.get("/tickets/", response_model=Ticket, status_code=200)
async def read_tickets(...):
    ...
    return tickets_db.values()   # many tickets, but response_model says "one Ticket"
After (fixed) 
from typing import List

@app.get("/tickets/", response_model=List[Ticket], status_code=200)
async def read_tickets(...):
    ...
    return list(tickets_db.values())

Why it happened

response_model=Ticket likely copy-pasted from the single-ticket endpoints (create_ticket, read_all_tickets) without reconsidering that this endpoint returns a collection.

How to avoid it next time

  • For every endpoint ask: "what does this function actually return?" and "one item, or many?" Model describes the real return shape, not a copied neighbor's.
  • Singular endpoint (/tickets/{id}) → Ticket. Collection endpoint (/tickets/, no ID) → List[Ticket].
  • Test via /docs Swagger UI — shape mismatch shows immediately as validation error or wrong response.
💡 Learn this: response_model isn't documentation only — FastAPI actively validates/filters outgoing data against it. Wrong shape can raise ResponseValidationError at runtime or silently strip data a client expected. Treat it as a promise to every consumer of the API.

5. Two FastAPI() instances — one silently orphaned

TL;DRapp = FastAPI() ran twice. Second call replaces the name's target; first app (with /health attached) is discarded.

What happened

app = FastAPI() at line 8 — /health route registered on that instance. Then app = FastAPI(lifespan=lifespan) at line 55 creates a brand-new, separate app object and rebinds the name app to it. The original instance (with /health attached) is unreferenced and garbage-collected — /health disappears from the running server even though the decorator looks correct in source.

Traced step by step

1. app = FastAPI() ← name "app" → Object A 2. @app.get("/health") ← /health registered on Object A 3. app = FastAPI(lifespan=...) ← name "app" → Object B (new, empty) Object A still exists in memory, but nothing points to it → garbage collected → /health gone 4. @app.post("/tickets/") ← registered on Object B (the only one left)
Before (broken) 
app = FastAPI()

@app.get("/health")
async def health_check():
    return {"status": "ok"}

@asynccontextmanager
async def lifespan(app: FastAPI):
    ...

app = FastAPI(lifespan=lifespan)   # NEW app — /health route is gone
After (fixed — create app once, with lifespan from the start) 
@asynccontextmanager
async def lifespan(app: FastAPI):
    ...

app = FastAPI(lifespan=lifespan)   # single instance, created after lifespan is defined

@app.get("/health")
async def health_check():
    return {"status": "ok"}

Why it happened

Own comment flags it: "i dont know again what this does, but this is what the format is, so i added this." Copying a pattern (FastAPI(lifespan=lifespan)) without checking whether app already existed led to a silent duplicate.

How to avoid it next time

  • Before reassigning a name already used (app = ... again), ask: "did I already create this, and am I about to throw away work attached to it?"
  • lifespan must exist before FastAPI(lifespan=lifespan) — so move the single FastAPI() call to after the lifespan function definition, don't create a second app.
  • When copy-pasting a pattern from docs, read every line for what it assumes about existing code.
💡 Learn this: Reassigning a variable doesn't merge/update the old object — it just points the name somewhere new. The old object survives only if something else still references it; here nothing did, so garbage collection reclaims it along with every route registered on it. Common trap with singletons: FastAPI(), DB connections, loggers.

6. Using http.client.HTTPResponse instead of FastAPI's error handling

TL;DRImported the wrong HTTPResponse — a low-level client-side class, not a FastAPI response. Use raise HTTPException(...) instead.

What happened

File imports from http.client import HTTPResponse, uses HTTPResponse(status_code=404, content={...}) to signal errors. http.client.HTTPResponse is a low-level class for reading raw HTTP responses from sockets (used when your code acts as an HTTP client) — not part of Starlette/FastAPI's response system, won't produce a proper 404 to the caller.

Two different classes, same-sounding name

ClassWhere fromActual purpose
http.client.HTTPResponsePython standard libraryreads a response after making an outgoing HTTP request (client role)
fastapi.HTTPExceptionFastAPIraise inside an endpoint to short-circuit with a proper error status + body (server role)
fastapi.responses.JSONResponseFastAPI (Starlette)return a fully custom response with headers/status/body (server role)
Before (wrong tool) 
from http.client import HTTPResponse
...
return HTTPResponse(status_code=404, content={"detail": "Ticket not found"})
After (FastAPI's actual error mechanism) 
from fastapi import HTTPException
...
raise HTTPException(status_code=404, detail="Ticket not found")

Why it happened

Name HTTPResponse "sounds right" for returning an HTTP response, but the standard library and FastAPI have separate, non-interchangeable classes with similar names for very different jobs.

How to avoid it next time

  • For errors in FastAPI: raise HTTPException(status_code=..., detail=...) — FastAPI catches it, converts to correct HTTP response.
  • fastapi.responses.JSONResponse only when you need to return (not raise) a custom response with full header/body control.
  • When importing something because "the name sounds right," check where it actually comes from.
💡 Learn this: raise HTTPException(...) vs. return matters — raising stops execution immediately and hands off to FastAPI's exception handling, exactly right for "this request is invalid, stop here." Returning a malformed object hands back garbage with a 200 status, because FastAPI has no idea it was meant as an error.

7. Fragile ID generation with len(tickets_db) + 1

TL;DRID from len() breaks after any delete — collection shrinks, next "new" ID collides with an existing ticket and overwrites it.

What happened

create_ticket generates new IDs as len(tickets_db) + 1. Works only while nothing is ever deleted. Once delete_ticket removes an entry, len(tickets_db) shrinks, and the next created ticket can be assigned an ID that already belongs to an existing ticket — silently overwriting it via tickets_db[ticket_id] = full_ticket.

Traced sequence

create ticket → len=0 → id=1 tickets_db = {1: A} create ticket → len=1 → id=2 tickets_db = {1: A, 2: B} delete id=1 → tickets_db = {2: B} create ticket → len=1 → id=2 (COLLISION) tickets_db = {2: C} ← B silently overwritten by C
Before (breaks after any delete) 
ticket_id = len(tickets_db) + 1
After (monotonically increasing, delete-safe) 
_next_id = 1  # module-level counter, separate from dict size

def get_next_id():
    global _next_id
    new_id = _next_id
    _next_id += 1
    return new_id

Why it happened

len(tickets_db) + 1 is a natural first guess for "next ID" — works for the happy path (only ever adding). Failure only appears once deletion enters the picture, easy to miss while writing the create endpoint in isolation.

How to avoid it next time

  • When deriving an ID from a collection's current size, ask: "does anything ever shrink this collection?" If yes, size-based IDs aren't safe.
  • Real database → auto-increment primary key or UUID. This in-memory dict → separate ever-incrementing counter (never decremented).
  • Manual test: create 2 tickets, delete ticket 1, create a new ticket — check whether the new ID collides with ticket 2's ID.
💡 Learn this: Deriving an ID from len() conflates "how many items exist right now" with "what's the next unique identifier to hand out." Only the same number if items are never removed. Separate counter decouples identity assignment from current collection size.

8. Duplicate keyword argument via ** unpack

TL;DRTicket(id=ticket_id, **ticket.model_dump()) passes id twice — once explicitly, once inside the unpacked dict (which already has an id key). Python raises TypeError: got multiple values for keyword argument 'id'.

What happened

The line tries to build a new Ticket by combining an explicit id=ticket_id with all fields spread out of ticket.model_dump(). Problem: ticket.model_dump() already includes an id key (every Ticket has an id field), so the same keyword argument gets supplied twice in one call — which Python forbids outright.

Piece by piece

PieceWhat it isWhat it does here
ticketexisting Ticket object from the loopthe source record being copied
.model_dump()Pydantic BaseModel methodconverts the object → a plain dict of all its fields, including id
**dict-unpacking operatorspreads a dict's key/value pairs as individual keyword=value arguments into a function call
id=ticket_idexplicit keyword argumentmanually sets id — but this key also exists in the unpacked dict → collision
Ticket(...)constructor callbuilds a new Ticket instance from whatever keyword arguments end up assembled

Traced with real values

ticket_id = 1 ticket = Ticket(id=1, title="Sample Ticket 1", priority="HIGH", reported_by="User A", is_resolved=False) ticket.model_dump() → {"id": 1, "title": "Sample Ticket 1", "priority": "HIGH", "reported_by": "User A", "is_resolved": False} Ticket(id=ticket_id, **ticket.model_dump()) expands to: Ticket(id=1, id=1, title="Sample Ticket 1", priority="HIGH", reported_by="User A", is_resolved=False) ↑ same keyword "id" supplied twice → TypeError: got multiple values for keyword argument 'id'
Before (broken) 
filtered_ticket[ticket_id] = Ticket(id=ticket_id, **ticket.model_dump())
# TypeError: __init__() got multiple values for keyword argument 'id'
After — Option A: id is already correct, skip rebuilding entirely 
filtered_ticket[ticket_id] = ticket   # ticket already IS the Ticket with the right id
After — Option B: need to override id, exclude it from the dump first 
filtered_ticket[ticket_id] = Ticket(id=ticket_id, **ticket.model_dump(exclude={"id"}))
After — Option C: idiomatic Pydantic way to clone-with-override 
filtered_ticket[ticket_id] = ticket.model_copy(update={"id": ticket_id})

Why it happened

.model_dump() dumps every field on the model — there's no implicit assumption that it excludes fields you're about to set manually. Manually setting id= on top, without first checking whether id is already in the dump, is what creates the collision. The intent ("make sure this new object has the correct id") was reasonable — the mechanism used to express it wasn't.

How to avoid it next time

  • Before writing func(explicit_kw=x, **some_dict), ask: "does some_dict already contain the key explicit_kw?" If yes, you must either drop the explicit kwarg, or exclude that key from the dict first.
  • Same rule as writing func(x=1, x=2) by hand — not allowed, just less obvious when one of the x= is hidden inside a **dict.
  • For Pydantic specifically, reach for model_dump(exclude={...}) or, better, model_copy(update={...}) when the actual goal is "same object, but override one or two fields." model_copy exists exactly for this and avoids the whole dump/unpack dance.
  • If the object is already fully correct as-is (no fields need overriding), don't rebuild it at all — just reference it directly.
💡 Learn this: **dict unpacking is great for "take this dict, spread it as keyword arguments" — but Python still enforces that each keyword argument name appears at most once in a call, regardless of whether it came from an explicit key=value or from inside an unpacked dict. Always check whether your unpacked dict already contains a key you're also setting manually. Pydantic's model_copy(update={...}) is the cleaner, purpose-built tool for "clone this object but change a couple of fields" — it sidesteps this whole class of bug.

How to think before each decision (general framework)

Every mistake above traces back to skipping one of these questions. Run through them before writing the line, not after debugging it.

1
What type is this value, right now? Before calling a method or using []/. access, know whether you're holding a dict, a list, or a model instance. If unsure, check your editor's inferred type.
2
What will I do with this container later? Choose dict vs. list vs. set based on the operations you'll perform (lookup by key vs. iterate in order vs. build up a sequence) — not by habit.
3
Say the condition in plain English first. Translate "keep this ticket if X" into code field-by-field, rather than pattern-matching on how a similar line looked elsewhere.
4
Does my declared contract match what I actually return? For FastAPI, response_model shape (single vs. list) must match the real return value — check both ends, not just one.
5
Am I creating something new, or reusing something that already exists? Reassigning a name like app = ... a second time silently drops whatever was attached to the first one. Check if the name is already bound before rebinding it.
6
Am I using the tool built for this framework, or one that sounds similar? Double-check imports — a same-sounding class from a different part of the standard library (http.client.HTTPResponse vs. FastAPI's HTTPException) is not interchangeable.
7
What happens under deletion / edge cases, not just the happy path? ID generation from len() is the clearest example — trace what happens after a delete, an empty collection, or a repeated operation before trusting the logic.
8
If I'm combining explicit kwargs with **dict, do the keys overlap? Check whether the dict you're unpacking already contains a key you're also setting manually. If it might, exclude that key from the dict or drop the explicit kwarg.
9
Did I actually run it? Every bug above surfaces immediately by hitting the endpoint once (via /docs or curl). Code that "looks right" is not the same as code that runs correctly.
